# Architecture

## Source of truth

**Postgres is the durable record of every job. Redis is only the delivery mechanism.** Redis
carries job ids from the API to workers; everything else (payload, status, attempts, results,
errors) lives in Postgres. If Redis is wiped, jobs can be re-enqueued from Postgres. If Postgres
is wiped, history is gone. That asymmetry is deliberate.

## Components

```
 client ──► API (FastAPI) ──► Postgres        jobs · attempts · dead_letters
               │
               └──────────► Redis Stream      tq:stream:<queue>   (consumer group "workers")
                                 │
                    worker 1 ◄───┤
                    worker 2 ◄───┤            each worker runs tasks in a child process
                    worker N ◄───┘
```

| Component | Code | Responsibility |
|---|---|---|
| API | `backend/app/api/jobs.py` | Validate, save the job, push its id to Redis |
| Queue | `backend/app/core/queue.py` | Thin wrapper over a Redis Stream + consumer group |
| Registry | `backend/worker/registry.py` | Maps a task name to a Python function (`@task`) |
| Executor | `backend/worker/executor.py` | Runs one task in a child process; kills it on timeout |
| Runner | `backend/worker/runner.py` | The loop: read, mark running, execute, save, ack |

## Schema

**`jobs`**: one row per job.

| Column | Notes |
|---|---|
| `id` (uuid) | Primary key, generated by the app |
| `queue`, `task_name` | Which queue; which registered function the worker runs |
| `payload` (jsonb) | Becomes the task's keyword arguments |
| `status` | `queued`, `running`, `retrying`, `succeeded`, `dead`, `cancelled` (varchar, not a native enum, so adding a state needs no `ALTER TYPE`) |
| `priority` | 0-9, higher runs first |
| `attempts` / `max_attempts` | Tries so far / allowed tries |
| `run_at` | Earliest start time; covers delayed jobs and retry backoff |
| `idempotency_key` | Optional; unique per `(queue, key)` |
| `result`, `last_error` | Outcome of the most recent attempt |
| `created_at`, `updated_at`, `started_at`, `finished_at` | Timestamps (UTC) |

Indexes: unique `(queue, idempotency_key)`; `ix_jobs_claim (queue, status, priority, run_at)`
for the later "next due job" query.

**`attempts`**: one row per execution try (worker id, start/finish, outcome of `succeeded`,
`failed` or `timeout`, and the error). Written by the worker from Phase 2.

**`dead_letters`**: one row per job that exhausted its retries, for inspection and replay.
Created by the schema, written from Phase 3.

## Job lifecycle

```
            enqueue
               │
               ▼
 ┌──────── queued ◄──────────────┐
 │            │ worker reads     │ backoff elapsed / reaper requeue   (Phase 3)
 │            ▼                  │
 │         running ──fail──► retrying                                  (Phase 3)
 │            │                  │
 │         success        attempts == max
 │            ▼                  ▼
 │        succeeded            dead (+ dead_letters row)
 │
 └─ cancel ─► cancelled                                                (no API yet)
```

**Implemented today (Phase 2):** `queued → running → succeeded`, and `queued → running → dead` on
any failure (task error, timeout, unknown task). The `retrying` state, the dead-letter row and
cancellation exist in the schema but are not wired up yet.

## The Redis Stream

- **One stream per queue name:** `tq:stream:<queue>`, one entry per job: `{"job_id": "<uuid>"}`.
- **One consumer group, `workers`.** Redis hands each entry to exactly one consumer in the group,
  so several workers never take the same message.
- **`XADD`** to enqueue. **`XREADGROUP ... >`** to read: `>` means "entries never delivered to
  this group". It blocks, so idle workers don't poll in a loop.
- A delivered entry sits in the group's **pending list** (which consumer holds it, since when)
  until it is **`XACK`ed**. The queue then also `XDEL`s the entry so the stream doesn't grow
  forever. The pending list is what makes crash recovery possible (Phase 3).
- The group is created with id `0`, so entries added before the group existed are still
  delivered.

## The worker

For each message the worker (`runner.handle_delivery`):

1. Loads the job from Postgres. Missing job, or a status other than `queued` (cancelled, or a
   duplicate delivery of a job that already ran): **ack and skip**.
2. Marks it `running`, increments `attempts`, inserts an `attempts` row, commits.
3. Calls `execute(task_name, payload, timeout)`.
4. Saves the outcome (`succeeded` + result, or `dead` + error) and the attempt outcome, commits.
5. **Acks the message, last.**

**Why a child process.** Python cannot stop a running thread, so a thread-based timeout would only
stop *waiting* while the task kept running. The executor starts each task in a child process
(`spawn`, so it inherits no database or Redis connections) and `kill()`s it when the timeout
passes. The child reports success or the traceback through a pipe; a child that dies without
reporting (crash, OOM kill) becomes a failed attempt, not a worker crash. Cost: about 0.1 s of
process start-up per job.

**Shutdown.** `SIGTERM` / `Ctrl+C` sets a flag; the worker finishes the current job and exits.
Compose gives the container a 70 s grace period (longer than the 60 s task timeout).

## Delivery guarantee: at-least-once

The ack comes **after** the result is saved. Therefore:

- A job is never *lost* because a worker died: its message stays pending in Redis.
- A job can run **more than once** (for example a worker dies after finishing the task but before
  the ack). Exactly-once delivery isn't achievable here, so **tasks should be idempotent**. The
  status check in step 1 blocks the most common duplicate: a redelivered message for a job that
  already finished is acked without running again.

Tests that pin this down: `test_message_is_acked_only_after_the_result_is_saved` and
`test_unexpected_error_leaves_message_unacked_so_it_is_not_lost`.

## Failure modes

| What fails | What happens today | Fixed by |
|---|---|---|
| Task raises an exception | Attempt `failed`, job `dead`, message acked | Phase 3: retry with backoff first |
| Task exceeds the timeout | Child killed, attempt `timeout`, job `dead` | Phase 3: retry |
| Task process crashes / is OOM-killed | Reported as a failed attempt | Phase 3: retry |
| Unknown task name | Job `dead`, `unknown task: ...` | n/a (not retryable) |
| Worker killed mid-job | Message stays pending in Redis; job stuck `running` | Phase 3: reaper |
| Worker killed (SIGKILL) | Same, plus the task's child process may keep running as an orphan and finish the task | Phase 3: reaper; tasks must be idempotent |
| API crashes between saving and pushing to Redis | Job `queued` in Postgres, never delivered | Phase 3: sweep re-enqueues |
| Redis down when a job is created | API still returns `201` and logs the error; job `queued`, not delivered | Phase 3: sweep re-enqueues |
| Postgres down while a worker is processing | Exception; message not acked, stays pending | Phase 3: reaper |
| Job has a future `run_at` | Stored but not delivered | Phase 4: scheduler |

**Heads-up for Phase 3.** The runner skips any job whose status isn't `queued`. A job that was
`running` when its worker died would therefore be skipped (and acked!) when the reaper redelivers
it, which would silently lose it. The Phase 3 runner has to treat "`running` with a stale start
time" as reclaimable.

## Idempotent enqueue

If `idempotency_key` is supplied and a job with the same `(queue, key)` exists, the API returns
that job (`200`) instead of creating another (`201`). A pre-check handles the common case; the
**unique constraint is the real guard**, and the repository catches the `IntegrityError` to
resolve concurrent duplicates. Verified against Postgres: 48 concurrent requests with one key
produced exactly one job. (A request that matched an existing key never re-publishes to Redis;
the Phase 3 sweep covers the case where the original publish failed.)

## Decisions

- **Redis Streams, not lists or pub/sub.** Consumer groups and the pending list give
  acknowledgments and crash recovery without building them by hand.
- **Sync SQLAlchemy 2.0 + psycopg 3.** Simpler to reason about and test than async at this stage.
  The database layer is isolated behind `repository.py`.
- **Process-per-task with `spawn`.** Real, enforceable timeouts and no shared connections, in
  exchange for start-up cost per job.
- **Payload as keyword arguments** (`func(**payload)`), as in Celery and RQ. Task functions stay
  plain and easy to test.
- **Application-side timestamps and UUIDs.** Identical behaviour on Postgres and on the SQLite
  used by fast tests.
- **Tests run on SQLite with a fake queue; real Postgres and Redis are verified separately.**
  The migration, the idempotency race and the worker loop were each run against the real
  services. CI does not run Postgres or Redis yet.
