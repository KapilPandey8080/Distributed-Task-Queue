# Architecture

## Source of truth

**Postgres is the durable record of every job. Redis (from Phase 2) is only the delivery
mechanism.** If Redis is wiped, jobs can be re-enqueued from Postgres; if Postgres is wiped,
history is gone. That asymmetry is deliberate.

## Schema (Phase 1)

**`jobs`**: one row per job.

| Column | Notes |
|---|---|
| `id` (uuid) | Primary key, generated by the app |
| `queue`, `task_name` | Which queue; which registered function the worker runs |
| `payload` (jsonb) | Arguments for the task |
| `status` | `queued`, `running`, `retrying`, `succeeded`, `dead`, `cancelled` (varchar, not a native enum, so adding a state needs no `ALTER TYPE`) |
| `priority` | 0-9, higher runs first |
| `attempts` / `max_attempts` | Tries so far / allowed tries |
| `run_at` | Earliest start time; covers delayed jobs and retry backoff |
| `idempotency_key` | Optional; unique per `(queue, key)` |
| `result`, `last_error` | Outcome of the most recent attempt |
| `created_at`, `updated_at`, `started_at`, `finished_at` | Timestamps (UTC) |

Indexes: unique `(queue, idempotency_key)`; `ix_jobs_claim (queue, status, priority, run_at)`
for the Phase 2+ "next due job" query.

**`attempts`**: one row per execution try (worker id, start/finish, outcome, error). Written
from Phase 2/3.

**`dead_letters`**: one row per job that exhausted its retries, for inspection and replay.
Written from Phase 3.

## Job lifecycle

```
            enqueue
               │
               ▼
 ┌──────── queued ◄──────────────┐
 │            │ worker claims    │ backoff elapsed / reaper requeue
 │            ▼                  │
 │         running ──fail──► retrying
 │            │                  │
 │         success        attempts == max
 │            ▼                  ▼
 │        succeeded            dead (+ dead_letters row)
 │
 └─ cancel ─► cancelled
```

Phase 1 implements only the first transition (a job is created as `queued`). The rest arrive
with the worker (P2) and reliability work (P3).

## Idempotent enqueue

If `idempotency_key` is supplied and a job with the same `(queue, key)` exists, the API returns
that job (`200`) instead of creating another (`201`). A pre-check handles the common case; the
**unique constraint is the real guard**, and the repository catches the `IntegrityError` to
resolve concurrent duplicates. Verified against Postgres: 48 concurrent requests with one key
produced exactly one job.

## Decisions

- **Sync SQLAlchemy 2.0 + psycopg 3.** Simpler to reason about and test than async at this
  stage. Workers can still be async later; the DB layer is isolated behind `repository.py`.
- **Application-side timestamps and UUIDs.** Keeps behaviour identical across Postgres and the
  SQLite used by fast unit tests.
- **Tests run on SQLite; migrations are verified on Postgres.** Postgres-specific behaviour
  (JSONB, timestamptz, the idempotency race) was checked against a real server.
